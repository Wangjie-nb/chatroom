# 熊出没聊天室 — 系统架构设计文档

> 一份面向简历 / 面试 / 代码评审的技术说明。描述核心设计取舍、线程模型、协议、数据层与游戏引擎。

---

## 1. 系统总览

一个 **C++17 实现的高并发 WebSocket 聊天室 + 小游戏联机平台**。

- **服务端**：单进程、多线程，基于 Linux `epoll` 的事件驱动网络模型，手写 WebSocket 握手与帧编解码，无第三方网络库。
- **客户端**：原生 HTML / CSS / JavaScript + Canvas，无框架、无构建步骤，浏览器直接运行。
- **持久化**：SQLite（用户、消息历史、朋友圈、收藏）；Redis（可选，在线列表 + 消息缓存）；无 Redis 时退化为纯内存。
- **小游戏**：象棋、五子棋、三消、贪吃蛇、坦克大战、枪战肉鸽 —— 逻辑全部在 C++ 引擎头文件中实现（纯状态机），前端只做渲染与输入；单机 / 联机双模式。

```
                     ┌────────────────────────────────────────────┐
  手机 / 电脑 / 平板  │                C++ Server                  │
  (浏览器)           │                                            │
 ┌──────────┐  HTTP  │  ┌──────────────────────────────────────┐  │
 │ 静态页面   │───────▶│  │  Reactor 主线程 (accept + 连接分发)    │  │
 │ www/*.html│        │  │  ┌────────────────────────────────┐  │  │
 └──────────┘        │  │  │  子线程1 (epoll + 事件处理)       │  │  │
   ▲      │          │  │  │  子线程2 (epoll + 事件处理)       │  │  │
   │  WebSocket      │  │  │  ...（one loop per thread）      │  │  │
   │  /ws 文本协议    │  │  └────────────────────────────────┘  │  │
   │  /upload 上传    │  │           │ 状态读取 / 写入             │  │
 └──┴──────┘         │  ┌───────────▼──────────────────────────┐ │
                     │  │ 数据层：SQLite / Redis / 内存          │ │
                     │  └──────────────────────────────────────┘ │
                     └────────────────────────────────────────────┘
```

## 2. 网络模型：epoll + Reactor 多线程

### 2.1 为什么选 epoll
- C10K 问题的经典解法，边缘触发（ET）+ 非阻塞 IO，事件复杂度 O(1)。
- 对比线程池 per-connection 模型：1 万连接只需少量线程，避免线程切换开销与栈内存爆炸。

### 2.2 one loop per thread
- **主线程**：`listen` → `accept` → 把新连接 fd 以负载均衡方式分发给某个子线程的 epoll 实例。
- **子线程**：各自持有独立 `epoll` + 事件循环，处理该连接上的可读/可写/异常事件。
- **优势**：
  - 单连接的读写**始终在同一线程**完成，天然无锁（关键设计点）。
  - 多核利用充分，线程数 = CPU 核数（或 *2），不随连接数增长。
- **写缓冲**：每个连接维护发送队列，可写事件触发时批量 `send`，减少系统调用次数。

### 2.3 连接管理
- 连接对象 `Handler`：持有 fd、发送缓冲、部分接收缓冲（处理 TCP 粘包 / 半包）。
- 遍历广播时**跳过已关闭连接**；优雅关闭先尝试发完缓冲再 close。
- 心跳：服务端定期 ping，客户端 pong；超时未响应踢下线（避免半开连接占资源）。

## 3. WebSocket 协议实现（手写）

- **握手**：HTTP Upgrade → 校验 `Sec-WebSocket-Key`，按 RFC 6455 用 `SHA-1 + Base64` 生成 `Sec-WebSocket-Accept`。
- **帧解码**：处理 FIN / opcode / mask / payload length（7bit / 16bit / 64bit 三种长度），分片消息（fragment）重组，客户端帧必须带 mask。
- **文本协议**：业务层为 `命令|参数` 文本协议，兼容中文（UTF-8），行分隔。
- **上行协议**：`/login <token>`、`/join <昵称>`、`/to 昵称 消息`、`/recall <id>`、`POST|...`、`FAV|...`、各游戏 `GUN|...` / `TANK|...` 等。
- **下行协议**：`MSGID|消息id|unix时间|发送者：内容`、`SYS|...`、`ONLINE|...`、`FAVS|...`、游戏状态帧等。

## 4. 线程模型与消息分发

```
        ┌────────────┐
        │ 主线程 accept│
        └─────┬──────┘
     round-robin 分发
        ┌─────┴──────┐
   ┌────▼─────┐ ┌────▼─────┐
   │ 子线程1   │ │ 子线程2   │    每个子线程：epoll_wait → 处理事件
   └────┬─────┘ └────┬─────┘
        │             │
        └──────┬──────┘
      共享数据：全局连接表（读多写少，用读写锁 / 无锁队列解耦）
```

- **游戏状态机**：每局游戏由独立引擎实例管理（如 `gun_engine.h`），引擎内部 `tick()` 按固定 tick 驱动；所有玩家输入先入队，tick 统一消费 —— 保证**确定性**与**同步一致**。
- **广播**：文本消息遍历连接表发送；游戏状态帧同样遍历，发送前统一序列化。
- **无锁解耦**：输入用无锁/有锁队列解耦接收线程与游戏 tick 线程，避免长时间持锁。

## 5. 数据层：三级存储

| 层级 | 技术 | 用途 | 说明 |
| --- | --- | --- | --- |
| 持久 | SQLite | users / messages / posts / favorites / avatars | 重启不丢，轻量零运维 |
| 缓存 | Redis (hiredis) | 在线列表、消息缓存 | 可选；无 Redis 退化为内存 |
| 内存 | 全局容器 | 在线连接表、游戏房间 | 高频读写，低延迟 |

- **密码安全**：`SHA-256(随机盐 + 密码)`，每用户独立 16 字节随机盐，库中不存明文。
- **会话**：登录发放 `token`（时间+序列+pid 组合），断线重连凭 token 恢复昵称 / 房间。
- **消息时间戳**：所有消息携带 unix 秒，前端按本地时区渲染，避免时区偏差（曾修复过"8 小时前"问题）。
- **撤回**：服务端真正删除该条消息并广播撤回事件，历史记录（SQLite/Redis/内存）同步标记，重进不再出现。

## 6. 小游戏引擎设计（C++ 纯状态机）

统一模式，6 款游戏共用一套骨架：

```
输入（玩家操作）──▶ 引擎状态机（C++）──▶ 序列化状态帧 ──▶ 前端 Canvas 渲染
                        │
                   tick() 定时推进（AI / 物理 / 波次）
```

- **引擎头文件**（`chess_engine.h` / `gun_engine.h` 等）：纯逻辑，`init()` / `tick()` / 输入接口 / `dump_state()` 序列化。
- **确定性**：同一输入序列 → 同一状态，便于联机同步与断线重连恢复。
- **联机**：创建房间（可配参数：棋盘大小、生命、难度、食物数量、步时限制等）→ 房间码 / 聊天室邀请 → 双方 `准备` → 开局 → 结束可再来一局（需双方准备）。
- **单机**：同一引擎本地跑，无需网络。

### 各游戏要点
| 游戏 | 引擎 | 亮点 |
| --- | --- | --- |
| 象棋 | chess_engine.h | 完整走子规则、将军/吃子特效、悔棋需对方同意、超时判负、先手后手可选 |
| 五子棋 | gomoku.html | 双人联机、再来一局 |
| 三消 | tile_magic_engine.h | DFS 回溯**可解性校验**、槽位堆叠、牌多难度可控 |
| 贪吃蛇 | snake_engine.h | 双人争食互杀、蛇头碰撞判定（比长度/平局）、加速有长度代价 |
| 坦克大战 | tank_engine.h | 可破坏/不可破坏墙体、一颗子弹一堵墙、弹夹换弹、地图规模/生命可配、斜向移动 |
| 枪战肉鸽 | gun_engine.h | 波次难度递增、经验**每人独立**、升级三选一**不暂停游戏**、弹夹/点燃/中毒/减速等 Buff |

## 7. 前端架构

- **零依赖**：原生 HTML/CSS/JS，无框架、无构建、无 CDN 依赖（离线可用）。
- **通信**：浏览器原生 `WebSocket`，文本协议与 C++ 引擎对应。
- **渲染**：游戏用 `<canvas>` 每帧重绘；聊天室用 DOM 增量渲染 + 消息自动滚动。
- **适配**：响应式布局，窄屏下控件触控友好（≥44px 点击区）。
- **存储**：`localStorage` 记住昵称 / 头像 / 提示音开关等偏好。

## 8. 部署架构（生产）

```
                  ┌──────────────────────────┐
 用户浏览器 ──HTTPS──▶ Nginx (443)             │
                  │  - 静态文件 www/          │
                  │  - /ws  反代 8888 (长连接) │
                  │  - /upload 反代           │
                  │  - /api  反代 (登录注册)   │
                  └──────────┬───────────────┘
                             │
                  ┌──────────▼───────────────┐
                  │  C++ Server 127.0.0.1:8888│
                  └──────────────────────────┘
```

- **为什么反代**：Nginx 处理 TLS 终结、静态文件、限流、上传体积限制（`client_max_body_size`）；C++ server 专注业务。
- **HTTPS 必要性**：浏览器安全策略只允许在 HTTPS / localhost 下调用 `getUserMedia`（语音功能），公网必须 HTTPS（Certbot 免费证书）。
- **启动**：`nohup ./server www > server.log 2>&1 &`；改动 `www/*.html` 无需重启。

## 9. 性能与压测

压测脚本 `tools/benchmark.py`（基于 websockets 库，并发连接 + 定时发消息 + 统计延迟）。

实测（4 核云服务器，200 并发 / 60s）：

| 指标 | 数值 |
| --- | --- |
| 成功连接 | 188/200（94%） |
| 发送速率 | ~173 条/秒 |
| 接收速率 | ~15,000 条/秒 |
| P99 延迟 | ~9.95s（满负载下） |
| 错误 | 12 次握手超时（连接数触及上限） |

> 结论：作为 C++ 学习/课程设计/简历项目，架构与实现已具备工程完整性；要进一步提升吞吐可继续优化（见第 10 节）。

## 10. 已知边界与优化方向

- **延迟**：满负载下 P99 偏高，源于单机广播 + SQLite 写放大。优化方向：
  - 批量发送（合并多次 `send`）
  - 消息队列解耦：接收线程 → 无锁队列 → 发送线程
  - 提高 TCP 发送缓冲、`SO_REUSEPORT` 多监听
- **持久化**：高频消息可先入 Redis / 内存，异步批量落 SQLite。
- **安全**：当前为小型内网/学习项目；生产可加 WSS、消息长度限制、接口限流、SQL 参数化（已用 prepare）、上传类型白名单。
- **扩展**：多进程 + 一致性哈希分片；或引入真正的 MQ（如 Kafka）做跨进程广播。
